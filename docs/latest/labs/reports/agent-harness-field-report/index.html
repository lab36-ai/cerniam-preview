Agent Systems / Research Cycle 02

The Agent Harness
as an operating system for work.

A field report on context economics, multi-agent topology, collaboration, deterministic build controls, worktree governance, and resource pressure in a live agent-operated development environment.

Abstract

The useful unit of agent engineering is not the model call. It is the controlled work interval around the model call.

Cerniam Labs and Lab 36 have been operating multiple persistent, named agents against real repositories, services, research records, and deployment surfaces. The work produced an Agent Harness that now spans identity, context recovery, routing, collaboration, execution lanes, deterministic verification, delivery, host admission, worktree lifecycle, and receipts. It did not arrive as one framework. It emerged from repeated failures at the boundaries between otherwise capable agents.

The central finding is that agent quality depends less on adding more intelligence to the prompt than on making ownership, authority, context, capacity, and proof explicit outside the prompt. Shared memory can attract several agents to the same valuable seam. Parallel workers can improve coverage while exhausting a host. A green review can still fail to deliver a commit. A smaller context window can save tokens while quietly charging a recovery tax on every serious turn. Each failure led to a control that could be inspected, tested, or receipted.

The resulting harness should be understood as an operating system for work: it admits context, assigns a lane, resolves an executor, constrains resources, records state transitions, and establishes what counts as completion. The model remains important, but it is one replaceable component inside a larger system.

Implemented

Execution controls

Workstream events, Operator routing, Forge preflight and delivery gates, build leases, pressure admission, source-only worktrees, and enforcement receipts.

Partially implemented

Economic controls

Context-budget receipt events and UI exist; automatic source-by-source token accounting and measured break-even policy do not.

Open research

Full fleet acceptance

Five isolated agent lanes with exact previews under measured host pressure, bounded review fan-out, and zero OOM or source drift.

01

The system under study

The research environment is a split execution estate. LabOps1 is a 31 GiB Linux VPS carrying long-lived services, agent profiles, repositories, worktrees, receipt ledgers, and build tooling. Freedom is a Mac Mini used for Apple-silicon, local-model, subscription-CLI, and overflow build workloads. Topic Places supplies durable collaboration and workstream authority. Hermes and other harnesses provide model-facing execution. Operator resolves agents across hosts and harnesses. Forge coordinates code-building and review workflows. A separate build fabric governs host capacity and generated build trees.

This arrangement matters because it exposes failures hidden by single-agent demos. Several agents may be correct about the same architecture and still collide in the same repository. Several builds may be individually reasonable and collectively overload the host. A session may retain enough context to be expensive but not enough to preserve authority. The research question therefore became operational:

How do we let multiple capable agents work quickly without allowing
context drift, ownership collisions, resource collapse, false completion,
or model output to become ungoverned system authority?

03

Multiple agent topologies

Two broad organizational styles recur in the research: pools of peers and hierarchies of responsibility. The field work shows that both are necessary. The mistake is treating one as a universal answer.

Single specialist lane

One agent owns the task in one isolated workspace. Deterministic validation runs outside the agent, and a separate reviewer may inspect the result. This is the cheapest topology when the task is narrow and the specialist fit is strong. It also minimizes merge and host pressure.

Peer pool

Several equal workers receive the same or partitioned objective. Forge supports parallel dispatch and restores result order to dispatch order rather than finish-time order. The five-agent build-fabric proof admitted two light jobs at a time and completed five jobs in waves of 2, 2, and 1. Peer pools increase exploration and fault coverage, but they also multiply model cost, build pressure, and correlated assumptions.

Current limitation: Forge’s parallel strategy reviews and delivers only the lowest-index successful workspace. Other workers may produce useful branches, but the present state machine does not independently review, merge, or deliver all of them. The behavior is deterministic now, not complete.

Consensus panel

A builder can be followed by several independent reviewers with majority or unanimity policy. This separates generation from judgment and permits specialists—security, correctness, visual design, operations—to examine the same artifact. Consensus does not eliminate shared blind spots. A quorum is only meaningful when reviewers have genuinely different instructions, evidence, or models.

Hierarchy

An orchestrator decomposes work, uses Operator’s capability registry to select specialists, delegates bounded tasks, and reconciles the resulting artifacts. Hierarchy is appropriate when authority or information is naturally layered: research, implementation, verification, and deployment should not share the same permissions. The parent remains accountable for scope, evidence, and final delivery.

Human-agent seam

The AFI-0001 incident established a fifth topology: a human implementation lane beside agent source-evidence and target-contract lanes. Gus’s adapter work was exposed to moving assumptions from two agent workstreams. The resolution was not to remove agent memory or human participation. It was to define stable handoff artifacts and make the human lane first-class.

04

Agent Lanes and collaboration

Agent Lanes were introduced after coordination failures that ordinary task lists could not express. A lane binds a durable workstream to an owner, workspace, action boundary, and handoff. It is not a colored column on a board.

Lane pinning

AFI-0003 defines a pinned primaryAgentId. Related context is not authority. Another agent may support only through an explicit reassignment, team-up event, or read-only review role. Every active slice is expected to declare an owning agent, lane, scope, allowed actions, and forbidden actions. A staging slice therefore cannot be reported as production work.

Seam contracts

AFI-0001 records a concrete collision. Source Contracts and Data Hub/package agents independently approached adapter generation while a human adapter implementer worked in parallel. Shared architectural memory acted as an attractor: all three parties found the same useful seam. The missing control was execution-level ownership.

The correction split the seam into source evidence, canonical target contract, human implementation, and adapter runtime contract lanes. Work froze until stable artifacts—adapter_candidate_packet.v1 and adapter_runtime_handoff.v1—could be reviewed. This is the harness at its most useful: it turns “coordinate better” into named ownership, forbidden actions, and inspectable handoffs.

Collaboration surfaces

  • Topic Places preserves the durable record: workstream, membership, comments, checkpoints, acknowledgements, claims, completion, and receipts.
  • Construct is the room for ambiguity, joint reasoning, teaching, approval, and witness.
  • Agent Roster projects who owns each durable workstream and whether it is active, blocked, waiting, parked, or complete.
  • Operator resolves which agent and harness should receive a request, preserving session identity and signed transport proof.
  • Forge handoff moves a preflighted task envelope through queue, processing, delivery, failure, and immutable receipt directories using atomic filesystem renames.

The collaboration doctrine is place-native: work lives in a durable place rather than a disappearing chat thread. This reduces wrong-agent routing, preserves provenance, and makes “is another agent already working here?” a queryable relationship rather than human memory.

05

Context management and recovery economics

The project rejected a simple contest between “small context” and “large context.” Small windows reduce token burn and stale carryover, but they create a recovery tax. Identity, user preferences, skills, workstream authority, repository state, vault records, and prior sessions may all need to be reloaded before serious action. The relevant equation is:

Total cost = live context cost + recovery cost + mistake cost

The mistake term changes the conclusion. The cheapest prompt is not economical if it causes duplicate work, wrong-workstream mutation, stale deployment, or several retries. AFI-0002 therefore adopted the principle minimum reliable context, not minimum context.

Context-budget receipts

The Workstream API and UI can already append and display context-budget receipt events. The schema records receipt ID, type, summary, evidence references, actor, and time through the same append-only authority contract as checkpoints and reassignment. What has not yet been completed is automatic source accounting: exact or estimated tokens for memory, skills, registry, vault, repository reads, and tool-output reduction.

AFI-0002 remains open until measured receipts from real turns establish which sources dominate recovery cost and where resident context becomes cheaper than repeated calibration. The present numbers are design estimates, not billing telemetry.

06

Token management and budgeting

Token budgeting appears at three different layers and should not be collapsed into one number.

  1. Model-window budget controls how much context can be resident and when compression begins.
  2. Turn-recovery budget accounts for what must be reloaded to act correctly.
  3. Workstream budget combines time, cost, token, and host capacity limits for a job or session.

Forge adds a route-cost policy before execution. OpenRouter is rejected, headless Claude is rejected, misleading “local” aliases are rejected, and more than one local model lane under parallel strategy is rejected. Local routes assume a conservative 32,768-token context unless explicitly declared. Preflight resolves each worker, escalation target, and reviewer to a concrete route and records provider, model, endpoint, cost class, binary state, model exposure, context assumption, and policy violations.

This is budgeting as admission control rather than reporting after the bill. The policy has no skip flag. If the route is red, no worktree is created and no worker is dispatched. The larger Cerniam session contract extends the same idea to maximum context size, time, cost, token budget, expiry, heartbeat, data disclosure, capability grants, and side-effect ceiling.

07

Build guards and verified delivery

Build control evolved through two layers. Forge guards the software result. The build fabric guards the host.

Forge: fail closed on the artifact

  • Schema and route preflight occurs before dispatch or worktree mutation.
  • Worker and reviewer timeouts are explicit.
  • Tracked and untracked changed files are both included in verification.
  • Built-in checks run before task-specific CI.
  • Reviewer output cannot become a passing verdict if the underlying dispatch failed.
  • Registry and session state are written atomically.
  • Retries rebuild from the original prompt rather than nesting previous retry scaffolds indefinitely.
  • A run cannot become passed until Git delivery is verified: repository present, staging successful, commit successful or verified no-op, HEAD advanced when expected, and index clean.

The delivery guard fixed a consequential defect. Earlier state could report success before proving that the commit landed. The current state machine records delivery_failed, carries the error into retry context, and exits non-zero.

Host build fabric: fail closed on capacity

LabOps1 now uses signed sprint leases bound to agent, workstream, repository, branch, permissions, and TTL. A weighted FIFO scheduler assigns light, medium, and heavy build classes against host units. Heavy jobs serialize and cannot starve behind newer light work. Local admission reads free disk, available memory, and full memory/I/O pressure stall information. Remote provider builds consume zero local units but retain provider timestamps.

The default lifecycle creates a controller-managed source-only worktree, predicts the smallest truthful build scope, admits it against policy, acquires a host-wide heavy-build lease, hydrates dependencies, builds, writes a receipt, removes generated outputs, and releases the worktree back to source-only state.

The active policy refuses heavy work below 80 GiB free disk, below 8 GiB available RAM, below a 4 GiB minimum projected peak, above I/O full-PSI 2.0, or above memory full-PSI 1.0. Severe pressure across three samples triggers process-group stop-loss.

08

Build-tree and worktree management

Parallel agents require filesystem isolation, but worktrees become a resource estate of their own. Each can accumulate node_modules, .next, .turbo, coverage, and dist. On a shared host, these trees consume disk, warm caches, file watchers, process references, and eventually human attention.

Source-only lifecycle

The lifecycle controller treats generated dependency and build trees as temporary hydration, not durable work. Clean, inactive managed worktrees return to source-only posture after build or completion. Unknown or global changed paths fail closed rather than invoking an all-zone build by accident.

Cold-estate consolidation

Clean inactive worktrees are pinned under archival Git refs before ordinary removal. Dirty inactive trees require a binary tracked patch and a private mode-0600 archive of non-generated untracked and ignored files. Generated dependency/build trees are never archived. Active, process-referenced, symlinked, mounted, recently changed, or restoration-ambiguous trees are refused.

Policy drift discovered during this review

Documented cap and active cap disagree

The lifecycle README states that the Console estate permits at most 10 registered worktrees. The active cerniam.build_lifecycle_policy.v2 file currently permits 25. The code validator accepts values from 6 through 25. Until reconciled, the machine-enforced boundary is 25, not 10.

This is a small example of why policy must be inspected from the running authority rather than repeated from prose. The report recommends one canonical cap rendered into documentation and receipts from the policy file.

VPS overload: incident, diagnosis, and response

Observed incident

A Vite production build reached transformation and terminated with exit 143. Raising the Node heap to 4 GiB did not prevent termination. The host was also observed with 8 GiB of exhausted swap and heavy resident agent load during a separate build incident.

ProvenLarge heap alone did not solve it
Observed conditionSevere swap occupancy and concurrent resident load
Not provenKernel OOM killer as the sender

The evidence supports host resource pressure as the operating condition. It does not identify the precise SIGTERM sender in the preserved incident log. The report therefore avoids calling it an OOM kill. That distinction matters: a kernel OOM kill, systemd policy, external supervisor, manual termination, or later build guard all require different remediation.

Memory full-PSI was low at observation time, so the host was not in active memory collapse. Swap remained heavily occupied, however, which reduces confidence in burst capacity and makes available-memory plus PSI more useful than free memory alone.

How the harness attacks overload

  1. Prevent: reject builds below disk/RAM floors or above PSI limits.
  2. Serialize: allow one host-wide heavy-build lease while admitting limited light work.
  3. Bound: classify work by weighted capacity and enforce deadlines and pressure stop-loss.
  4. Isolate: build in managed source-only worktrees with scoped hydration.
  5. Dehydrate: remove generated trees after the useful artifact and receipt exist.
  6. Offload: move exact working-tree builds to Freedom or remote providers when local pressure is real; record them as zero-local-unit work.
  7. Enforce: stop unleased heavy-build process trees rather than merely auditing them.
  8. Prove: retain queue, claim, release, enforcement, preview, and exact-SHA receipts.

Enforcement record

Between August 1 and August 5, the guard wrote 240 verified enforcement receipts. Across those receipts it signalled 652 process IDs associated with 296 root-process mentions, with no remaining processes in the recorded outcomes. Child-process fan-out means these numbers must not be read as 652 independent builds. They do show that uncontrolled build invocation was systemic.

Operational caveat: the guard service log contains intermittent “enforcement error exit=1” entries alongside successful enforcement. The guard is active, but its own error rate, classification accuracy, and false-positive rate need a typed health rollup. A safety control that fails silently becomes another source of uncertainty.

10

Receipts, proof, and the meaning of done

The harness treats failure and denial as evidence rather than absence. Topic Places stores append-only workstream events. Operator signs consequential actions. Forge records review, CI, delivery, and failure state. The build fabric records admission, queue, claim, release, preview, source SHA, and enforcement. Partner-agent architecture requires canonical receipts for authorization and execution rather than trusting a partner’s success message.

This yields a strict completion rule:

agent says complete            ≠ complete
checks pass                    ≠ delivered
git commit exists              ≠ deployed
provider reports READY         ≠ correct revision
canonical artifact + receipt + independent verification = done

The rule is not ceremonial. Forge’s earlier delivery defect demonstrated that every prior stage could be green while the commit never landed. The fix moved delivery verification inside the passing state transition.

11

Authority and security boundaries

Models propose. Policy decides. Controlled services execute. Receipts prove.

This rule runs through the entire harness. Original asks are preserved as evidence but are not interpreted as authorization. A context pack distinguishes facts, evidence, model opinions, instructions, and policy constraints. Secret references remain references; reusable credentials do not enter model context. Tool grants, side-effect ceilings, approval posture, time, cost, token budgets, expiry, heartbeat, and revocation belong to the session contract.

The current Agent Workstream API illustrates the boundary in executable form. Any identified operator can read the registry. Mutation requires Super Admin authority. Server-owned actor and timestamps are attached to checkpoints, receipts, reassignments, stack changes, session links, archives, completions, and agent registrations. Duplicate action IDs are idempotent.

Operator similarly separates registry, transport, policy, and audit. Its Hermes adapter refuses secret-looking bodies because the non-interactive prompt channel currently uses command arguments. Secret-bearing work must use a harness with an API, stdin, or file channel. Public ingress remains incomplete, so the report does not describe Operator’s public gateway as production-ready.

12

Findings

  1. Shared memory improves architecture and increases collision risk. Multiple agents correctly identify the same valuable seam. Without lane ownership, intelligence converges faster than execution governance.
  2. Context compression is not free. It consumes provider time, can fail, and may force recovery reads later. Its economics must include recovery and mistake cost.
  3. Parallelism is a host policy, not a prompt preference. “Use five agents” has implications for model routes, local runtimes, builds, worktrees, reviewers, and merge behavior.
  4. Build trees are operational state. Dependency hydration, generated output, watchers, and stale worktrees materially affect host capacity.
  5. Completion is a state transition guarded by proof. Textual self-report, green review, and even a successful build are intermediate signals.
  6. Human work must be modeled as a lane. Otherwise agents treat a human implementer as an external detail and continue changing the contract around them.
  7. Budgets must compose. Token, route cost, wall time, host capacity, and authority are separate budgets that meet at one work interval.
  8. Control planes require their own observability. Guard errors, compression fallbacks, receipt failures, and policy drift are first-class operational events.

Recommended next research and engineering work

1. Complete automatic context receipts

Capture exact provider usage where available; estimate memory, skill, registry, vault, repository, and tool-output footprints otherwise. Record raw-versus-injected size and the reduction method. Collect at least five real turns per major turn class before changing global context policy.

2. Integrate lane and seam contracts into the live roster

The board already projects agents, workstreams, stack posture, sessions, checkpoints, and receipts. Add pinned-owner mismatch warnings, bounded team-up roles, slice tags, writable repositories, handoff artifacts, and convergence alarms.

3. Cap peer pools through the capacity scheduler

Replace Forge’s unbounded max_workers=len(worker_dispatch) behavior with policy issued by the host build fabric. Model dispatch and build execution should have separate limits.

4. Decide parallel review and merge semantics

Choose explicitly among first-success, per-worker review, consensus over artifacts, or merge-before-review. The current deterministic first-success behavior should remain visible until replaced.

5. Reconcile worktree cap policy

Resolve 10 versus 25, then generate documentation and dashboards from the canonical policy. Add a receipt when the cap changes.

6. Establish guard health metrics

Roll up enforcement attempts, successful signals, remaining processes, errors, false positives, and average response time. Alert on guard failure separately from build violation.

7. Treat swap recovery as an operational task

High swap occupancy after pressure has passed should be observed and explained. Do not clear swap blindly on a live host; measure working sets, idle services, and restart windows, then use a controlled recovery plan.

8. Run a bounded topology benchmark

Evaluate single specialist, peer pool, consensus panel, and hierarchy on the same task set. Measure completion quality, escaped defects, review burden, wall time, input/output/cached tokens, recovery tokens, host PSI, build queue time, collision rate, merge overhead, and cost.
